# Compare a visual change

Use for a requested comparison or an existing visual surface whose revision
benefits from visible evidence: a page, app view, slide, report or content asset.
New work without a baseline needs review of the actual result, not an invented
before-image. A small edit can use one focused pair in the existing task.

## Establish the baseline

Before editing, retain the relevant existing render when practical. Record the
source revision or artifact identity and the view/state being compared. Use an
available source, accepted prior capture or safe preview; do not reset a working
checkout or overwrite user work to reconstruct a baseline. If the before-state
is unavailable, state the limitation and inspect the after-state against the
brief. Do not manufacture a failure or call a reconstruction an observed baseline.

## Make the comparison fair

Capture the same meaningful area with comparable dimensions, viewport/zoom,
content/data and interaction state. For responsive work, pair the same viewport
on both versions. When the intended change includes content, dimensions or state,
identify that difference and keep other relevant conditions comparable. Avoid
cropping away a regression or comparing a loaded view with an unfinished one.

Use the task's existing browser, renderer or capture tools. Inspect both actual
captures and their source identity; filenames alone prove neither. A still pair
can demonstrate appearance. An interaction claim needs the corresponding action
and result; accessibility, correctness or performance claims need their relevant
checks. Visual preference alone does not establish improved usability.

## Return a useful comparison

Show the selected pair side by side where supported, or provide clearly labelled
before/after files or links. Briefly explain the visible change, how it serves the
accepted goal, and any tradeoff or unresolved regression. Use a short sequence
or recording only when a still pair cannot explain the selected behavior.

Keep the captures and observations with the project or current task's existing
evidence. Review Design owns the judgment and acceptance; update affected proof
after a further edit. Avoid a separate report for a simple comparison.

This method adds no capture dependency, upload service or automatic PR workflow.
Publishing images or sending evidence follows the task's existing destination
and action authority. A factory or project can automate capture and PR assembly
under its own workflow; those integrations remain independently owned.
